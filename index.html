1. Application Identity & Purpose

Operational scope, intended audience, and non-commercial internal-use declaration.

DobbyFetch is a private, containerized on-premise Data Warehouse (DWH) and Business Intelligence (BI) platform developed and operated solely by POL-ENSA Sp. z o. o. to support its own e-commerce operations.

The platform consolidates transactional, operational, inventory, customer support, and marketing performance data from the organization's own sales channels and internal enterprise systems into a central PostgreSQL 16 data warehouse. Authorized employees analyze business KPIs via internal Metabase dashboards and a strictly governed, read-only Model Context Protocol (MCP) Text-to-SQL interface.

Strict Internal-Use Declaration:
  • Not a Public SaaS: DobbyFetch is not offered, marketed, or licensed to external merchants, agencies, or third parties.
  • Single Merchant Organization: All connected marketplace, storefront, and advertising accounts belong exclusively to POL-ENSA Sp. z o. o..
  • Zero Data Resale or External Sharing: Data ingested from external APIs is never sold, rented, redistributed, or exposed to third parties.
  • Restricted User Base: Access is limited to approximately 10 authorized internal employees (operations, inventory specialists, and management) via private LAN/VPN.

2. Allegro REST API Integration Scope Read-Only

Explicit inventory of endpoints, polling cadence, authentication flow, and write-operation prohibition.

DobbyFetch connects to the merchant's own Allegro seller account exclusively to synchronize order history, billing/commission records, and offer metadata into the internal data warehouse for sales reconciliation and unit-economics reporting.

Method Endpoint Incremental Parameter Internal Analytical Purpose
GET /order/events from (cursor ID) Incremental ingestion of order lifecycle events and status transitions.
GET /order/checkout-forms updatedAt.gte Synchronization of order line items, quantities, payment status, and fulfillment metadata for sales reporting.
GET /billing/billing-entries occurredAt.gte Extraction of Allegro commissions, listing fees, and promotional charges for net profitability analysis.
GET /sale/offers Paginated snapshot Read-only catalog snapshot to map Allegro offer IDs to internal ERP SKUs and monitor active listings.
Zero Write Operations

Strictly Read-Only Access

DobbyFetch performs zero POST, PUT, PATCH, or DELETE operations on Allegro offers, prices, stock quantities, or customer orders.

Sync Cadence

15-Minute Incremental Polling

Scheduled ELT jobs run every 15 minutes using persisted high-water mark cursors (audit.etl_state) to fetch only newly created or updated records.

API Etiquette

Rate-Limit Aware & Resilient

Respects X-RateLimit-* headers, uses idempotent upserts, and applies exponential backoff with jitter on HTTP 429 and 5xx responses.

Authentication & Token Lifecycle

Authorization uses the OAuth 2.0 Device Flow suited for headless, on-premise backend services without exposing public callback endpoints. Access and refresh tokens are stored in a dedicated, access-controlled audit.endpoint_credentials table accessible only to the isolated ingestion service account, and refreshed automatically before expiration.

3. Other Supported Integrations

Unified multi-channel reporting across internal ERP, WMS, storefront, advertising, and support platforms.

To provide an accurate single source of truth for inventory availability, gross-to-net margin, and marketing return on ad spend (ROAS), DobbyFetch integrates with the following systems — all in read-only mode:

ERP (On-Premise)

Subiekt GT (MS SQL)

Direct read-only connection (READ UNCOMMITTED / WITH (NOLOCK)) extracting product master data, stock levels, warehouse definitions, VAT rates, and purchase cost baselines for internal COGS calculations.

E-Commerce Storefront

Shopify Admin API

Read-only incremental extraction of store orders and fulfillment events filtered via updated_at_min, respecting X-Shopify-Shop-Api-Call-Limit throttling headers.

Warehouse Management

Feniks WMS

Read-only synchronization of warehouse allocations, bin states, and batch inventory movements to reconcile physical stock with sales channels.

Marketing & Analytics

Google Ads, Meta, GA4, Search Console & Merchant Center

Read-only rolling lookback window extraction (3–7 days) of campaign spend, impressions, clicks, and attribution metrics to calculate channel-level ROAS and contribution margin.

Customer Support

Responso

Read-only ingestion of support ticket volumes, conversation metadata, and SLA response metrics to monitor internal customer service performance.

Data Modeling

dbt Semantic Layer

Standardizes raw JSONB payloads into unified analytical marts separating general operational metrics (analytics_generic) from sensitive financial margin models (analytics_restricted).

4. System Architecture

End-to-end containerized ELT pipeline, layered PostgreSQL 16 DWH, and governed internal consumption.

Figure 1: DobbyFetch high-level data flow — all ingestion connectors operate read-only into an isolated on-premise PostgreSQL 16 warehouse.

Layered Data Governance

  • raw Schema: Landing zone storing unmodified JSONB source payloads for lineage and replayability; strictly inaccessible to end users and BI tools.
  • analytics_generic Schema: Sanitized operational marts (products, daily orders, stock levels, traffic, support SLA) strictly excluding purchase costs, COGS, and profit margins.
  • analytics_restricted Schema: Managerial financial marts (order-item profitability, daily net margin, and governance audit reports) restricted solely to the manager role.
  • audit Schema: Pipeline run telemetry, incremental cursor state, managed OAuth credentials, MCP user RBAC policies, and immutable query audit trails.

5. Data Security & Access Controls

Defense-in-depth controls protecting API credentials, merchant data, and internal analytics access.

OAuth 2.0 Device Flow & Credential Protection

Marketplace tokens are provisioned via OAuth 2.0 Device Flow using least-privilege read-only scopes, stored securely inside the isolated audit.endpoint_credentials store, and never exposed to end-user BI or AI interfaces.

Network Isolation (Zero Public Ingress)

The PostgreSQL 16 database, Metabase BI server, ELT scheduler, and custom MCP server run inside isolated Docker containers on private on-premise infrastructure accessible solely over corporate LAN/VPN.

Per-User Authentication

Every internal employee authenticates with an individual account (email + high-entropy generated password). Passwords are never stored in plaintext and are protected using salted bcrypt/argon2 hashing.

Granular Table & Column RBAC

Dynamic per-user permissions (audit.mcp_permissions) enforce exact table- and column-level entitlements. Schema discovery dynamically strips unauthorized tables and columns so standard users never see restricted financial fields.

SQL AST Guardrails

Every query submitted through the MCP interface is parsed via SQL AST inspection (sqlparse) prior to execution: strictly SELECT-only, multi-statement queries blocked, unauthorized table/column references rejected, automatic LIMIT 100 row cap, and a 10-second statement timeout.

Immutable Audit Logging

Every analytical query requires a mandatory business intent reason and is recorded in audit.mcp_query_logs alongside user identity, SQL statement, status (SUCCESS / DENIED / ERROR), row count, and execution time. All ETL runs are logged in audit.etl_runs.

6. Data Retention & Administrator Contact

Internal data lifecycle management and technical point of contact for API providers.

Data Retention & Lifecycle

  • Transactional & Financial Analytical Data: Retained within the on-premise data warehouse for internal business intelligence, year-over-year historical analysis, and alignment with statutory Polish/EU accounting and tax record-keeping obligations.
  • Audit & Operational Logs: An automated daily retention job purges expired audit entries according to configurable organizational thresholds (default: 5 years / 1,825 days or 30 GB maximum log volume).
  • Token Revocation & Offboarding: Upon employee offboarding, individual user accounts and RBAC grants are immediately deactivated. If an external API integration is discontinued, its OAuth tokens are revoked and deleted from audit.endpoint_credentials.
